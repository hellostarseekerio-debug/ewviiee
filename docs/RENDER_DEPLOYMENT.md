# Deploying to Render

This deploys the same API image described in `docs/DEPLOYMENT.md` §4-6
(the repo-root `Dockerfile`, unmodified) as a Render Web Service, backed by
a Render-managed PostgreSQL instance, using the `render.yaml` Blueprint at
the repository root. No application code changes were required for this -
`render.yaml` only supplies environment variables the app already reads
(`app/core/config.py`).

`docker-compose.yml` remains the correct path for a self-hosted server;
this document is Render-specific and the two deployment paths don't
interact.

Read this whole document before clicking anything in the Render
dashboard - a few values need to be generated or decided upon before the
first deploy, and the checklist at the end explains what to verify
afterward.

## 1. Prerequisites

- A Render account (https://render.com).
- This repository pushed to GitHub, with Render granted access to it (or
  the specific repo) via GitHub's Render app installation.
- Two secrets you will generate locally in step 4, below, before you
  deploy.

## 2. What `render.yaml` provisions

Render Blueprints (`render.yaml`) describe infrastructure as code, similar
in spirit to `docker-compose.yml` but for Render's own platform. Applying
it creates:

- **`oap-postgres`** - a managed PostgreSQL database (`starter` plan,
  `oregon` region - change the region to whichever is closest to your
  office if needed). Not reachable from the public internet.
- **`oap-api`** - a Web Service built from this repository's `Dockerfile`,
  with:
  - A 5GB persistent disk mounted at `/app/data` (documents, exports,
    archives, logs, local backup copies - see step 9).
  - `OAP_POSTGRES_DSN` wired automatically to the database above.
  - `OAP_API_HOST=0.0.0.0` / `OAP_API_PORT=8000` so the container accepts
    traffic from Render's edge proxy (matches the same override
    `docker-compose.yml` already makes for the same reason - the app's
    own default of `127.0.0.1` is loopback-only and unreachable from
    outside the container).
  - `OAP_TRUST_PROXY_HEADERS=true` / `OAP_TRUSTED_PROXY_HOSTS=*` - Render
    terminates TLS and proxies every request at its edge, so the app must
    read the real client IP from `X-Forwarded-For` the same way it would
    behind a self-hosted nginx/Caddy (see `docs/DEPLOYMENT.md` §5).
    Without this, per-IP login rate limiting would treat every user in
    your office as one shared "IP" (Render's proxy address).
  - A health check at `GET /health`.

## 3. Step-by-step: creating the Blueprint

1. **Create the Render Postgres database and Web Service together via
   Blueprint:**
   - In the Render dashboard: **New +** -> **Blueprint**.
   - Connect the GitHub repository containing this code (grant Render
     access if this is the first time).
   - Render detects `render.yaml` at the repo root and shows a preview of
     the `oap-postgres` database and `oap-api` web service it will create.
   - **Do not click "Apply" yet** - continue to step 4 first, so the two
     manual secrets below are ready to paste in immediately after the
     resources are created (the service will fail to start without
     `OAP_ENCRYPTION_KEY`, by design - see `assert_secure_for_production()`
     in `app/core/config.py`).

   If you would rather do this by hand instead of via Blueprint (e.g. to
   review each setting individually):
   - **New +** -> **PostgreSQL**. Name it `oap-postgres`, database name
     `office_automation`, user `oap`, plan `Starter` or higher. Create it.
   - **New +** -> **Web Service** -> connect the same repository -> choose
     **Docker** as the runtime (Render auto-detects the `Dockerfile`).
   - Under the new service's **Environment** tab, add every variable
     listed in §4/§5 below by hand (the `fromDatabase` shortcut only
     works via Blueprint - copy the Postgres instance's **Internal
     Database URL** from its own dashboard page into `OAP_POSTGRES_DSN`
     instead).
   - Under **Disks**, add a disk named `oap-data`, mount path `/app/data`,
     size 5GB (or more, depending on expected document volume).
   - Under **Settings**, set the health check path to `/health`.

## 4. Secrets you must generate manually before deploying

Two values in `render.yaml` are intentionally left blank
(`sync: false`) because they cannot be safely auto-generated by Render:

- **`OAP_ENCRYPTION_KEY`** - must be a valid Fernet key, not just any
  random string (it encrypts MFA secrets and other sensitive fields at
  rest; a malformed value fails immediately). Generate one locally:

  ```bash
  python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
  ```

  Paste the output into the `oap-api` service's **Environment** tab
  under `OAP_ENCRYPTION_KEY`. **Back this up somewhere outside Render**
  (a password manager or your office's secrets vault) - losing it makes
  every encrypted value permanently unrecoverable, including if you ever
  need to restore from a database backup onto a fresh service.

- **`OAP_SECRET_KEY`** - `render.yaml` sets `generateValue: true`, so
  Render generates a strong random value for you automatically the first
  time the Blueprint is applied. No action needed, but if you ever
  regenerate it manually, keep it at least 32 characters (see
  `assert_secure_for_production()`) - a shorter or guessable value would
  let an attacker forge login tokens.

Optional, only if your office has decided to use a cloud AI provider (see
`docs/PRIVACY.md` - the default `OAP_AI_PROVIDER=local` sends nothing
off-service):
- `OAP_OPENAI_API_KEY`, `OAP_ANTHROPIC_API_KEY`, or the `OAP_AZURE_OPENAI_*`
  variables, set under the service's Environment tab. Leave blank
  otherwise.

## 5. Fixing `OAP_CORS_ALLOWED_ORIGINS` after the first deploy

`render.yaml` sets this to `["https://oap-api.onrender.com"]`, assuming
the service name `oap-api` is available and Render assigns exactly that
subdomain. Render appends a random suffix instead if that name is already
taken by someone else.

After your first deploy, check the actual URL shown at the top of the
service's dashboard page. If it differs from the assumed value, update
`OAP_CORS_ALLOWED_ORIGINS` under **Environment** to match exactly (must be
the same scheme/host your browser client is served from - the app
rejects a literal `"*"` outright in production), then let the service
redeploy. If you later add a custom domain, update this again to include
it.

## 6. Environment variables reference

| Variable | Set by | Value | Notes |
|---|---|---|---|
| `OAP_ENVIRONMENT` | render.yaml | `production` | Enables `assert_secure_for_production()` checks at startup. |
| `OAP_DATABASE_BACKEND` | render.yaml | `postgresql` | SQLite is not viable on Render - see step 8. |
| `OAP_POSTGRES_DSN` | render.yaml (`fromDatabase`) | auto | Points at the `oap-postgres` internal connection string. |
| `OAP_API_HOST` | render.yaml | `0.0.0.0` | Required - default (`127.0.0.1`) is unreachable from outside the container. |
| `OAP_API_PORT` | render.yaml | `8000` | Matches the Dockerfile's `EXPOSE 8000`, which Render auto-detects. |
| `OAP_TRUST_PROXY_HEADERS` | render.yaml | `true` | Required behind Render's edge proxy - see §2. |
| `OAP_TRUSTED_PROXY_HOSTS` | render.yaml | `*` | Safe here specifically because the container is only reachable via Render's proxy, never directly. |
| `OAP_SECRET_KEY` | render.yaml (`generateValue`) | auto | Auto-generated on first apply; back up if you rely on stable JWTs across a service recreation. |
| `OAP_ENCRYPTION_KEY` | **you, manually** | a generated Fernet key | See step 4 - required, no safe default. |
| `OAP_CORS_ALLOWED_ORIGINS` | render.yaml, **verify after deploy** | `["https://oap-api.onrender.com"]` | See step 5. |
| `OAP_RATE_LIMIT_LOGIN` / `OAP_RATE_LIMIT_DEFAULT` | render.yaml | `5/minute` / `120/minute` | Same production defaults as `.env.example`. |
| `OAP_AI_PROVIDER` | render.yaml | `local` | Change only after an explicit office decision - see `docs/PRIVACY.md`. |
| `OAP_OPENAI_API_KEY` / `OAP_ANTHROPIC_API_KEY` / `OAP_AZURE_OPENAI_*` | **you, manually, optional** | blank | Only needed if `OAP_AI_PROVIDER` is changed from `local`. |
| `OAP_MAX_UPLOAD_SIZE_BYTES` | render.yaml | `26214400` (25MB) | Unchanged from `.env.example`. |
| `OAP_BACKUP_RETENTION_DAYS` | render.yaml | `90` | Applies to `scripts/backup_db.py`'s pruning logic if run inside the service shell. |
| `OAP_DATA_DIR`, `OAP_LOCAL_IMPORT_ROOT`, `OAP_ARCHIVE_ROOT`, `OAP_EXPORT_ROOT`, `OAP_BACKUP_DIR`, `OAP_SQLITE_PATH` | *(not set)* | app defaults (`./data/...`) | Not overridden - already resolve under `/app/data`, the persistent disk's mount path, since the container's working directory is `/app`. |

Every other `OAP_*` variable in `.env.example` keeps its documented
default and does not need to be set for Render specifically.

## 7. Running database migrations

No separate step is needed. `docker/entrypoint.sh` - which the Dockerfile
uses unmodified as its `ENTRYPOINT` - already waits for the database to
accept connections and then runs `alembic upgrade head` automatically
before starting the API, on every deploy. Check the deploy's **Logs** tab
for lines like:

```
office-automation-platform: waiting for the database...
office-automation-platform: database is reachable.
office-automation-platform: running migrations (alembic upgrade head)...
office-automation-platform: starting application: ...
```

If you ever need to run a one-off Alembic command manually (e.g. to
inspect `alembic history`), use Render's **Shell** tab on the `oap-api`
service - it opens a shell inside the running container with the same
environment variables already set.

## 8. Creating the first administrator account

There is no open "create user" API endpoint (by design - see
`scripts/create_admin.py`'s docstring).

**If your plan includes Shell** (Starter and above), open the **Shell**
tab on `oap-api` and run:

```bash
python scripts/create_admin.py --username admin --full-name "Your Name"
```

You'll be prompted for a password (12+ characters, upper/lower/digit/
special character - the same policy enforced everywhere else in the app).

**If you're on the Free plan** (no Shell/SSH access), use the
environment-variable bootstrap instead - see `scripts/bootstrap_admin_from_env.py`.
On the `oap-api` service's **Environment** tab, add:

```
OAP_BOOTSTRAP_ADMIN_USERNAME=admin
OAP_BOOTSTRAP_ADMIN_PASSWORD=<a strong password - 12+ chars, upper/lower/digit/special>
```

Saving these triggers a redeploy. The container's entrypoint runs this
bootstrap automatically right after migrations, every time it starts: it
creates that account as admin if it doesn't exist yet, or - if it already
exists - resets its password, clears any lockout, disables MFA, and forces
the role back to admin (so this doubles as a "forgot my password" recovery
path, not just first-time setup). Check the **Logs** tab - every run always
logs something here (never silent), so you can tell exactly what happened:

```
office-automation-platform: admin bootstrap-from-env: both environment variables are set for username 'admin'.
office-automation-platform: admin bootstrap-from-env: 1 user(s) currently in the database; existing account for 'admin': found.
office-automation-platform: admin bootstrap-from-env: admin account 'admin' reset and committed to the database.
office-automation-platform: admin bootstrap-from-env: SECURITY - remove OAP_BOOTSTRAP_ADMIN_USERNAME and OAP_BOOTSTRAP_ADMIN_PASSWORD from this service's environment variables now and redeploy. Leaving them set resets this password on every restart.
```

If login still fails after seeing the "reset"/"created" line, the most
likely cause is that the password you typed into the Environment tab isn't
exactly the one you're typing at login (an extra trailing space from a
copy-paste, a different browser autofill value, etc.) - the variable's
value in the Environment tab is masked, so re-type both fresh rather than
trying to eyeball it. If you instead see the "skipped" line (missing
variable or a rejected weak password) or nothing about bootstrap at all,
double-check the exact variable names for typos.

Then log in with that username/password.

**Immediately after confirming you can log in, delete both environment
variables** from the Environment tab and let the service redeploy again.
This is the whole reason it's described as *temporary*: as long as those
two variables stay set, every restart (a crash, a manual redeploy, a
Render platform maintenance restart) silently resets that account's
password back to the same value - anyone who later learns it (a shared
screenshot, a support ticket, a misconfigured logging pipeline) could keep
regaining access indefinitely for as long as the variables remain. It is
never exposed as an HTTP endpoint and only ever runs inside the container
at startup, but it is only as safe as how promptly you remove it.

## 9. Deploying

1. Confirm `OAP_ENCRYPTION_KEY` is set (step 4) and
   `OAP_CORS_ALLOWED_ORIGINS` matches your actual service URL (step 5).
2. Click **Apply** (Blueprint) or **Create Web Service** (manual path).
   Render builds the Docker image and starts the container - watch the
   **Logs** tab for the migration output in step 7 and then a line
   indicating uvicorn is serving.
3. Confirm health: the **Events**/**Metrics** view will show the service
   as "Live" once `GET /health` starts returning `200`.
4. Test the live API:
   ```bash
   curl https://<your-service>.onrender.com/health
   # {"status": "ok", "app": "Office Automation Platform"}
   ```
   Then log in through the same frontend/API client documented in
   `docs/user_manual.md`, using the admin account from step 8, and
   confirm `POST /api/auth/login` and one authenticated `GET` (e.g.
   `GET /api/documents`) both succeed over HTTPS.

## 10. Backups on Render

`scripts/backup_db.py` only knows how to back up SQLite directly and
reminds you to use `pg_dump` for PostgreSQL - the same behavior it has in
every other deployment. On Render:

- **Render's own automatic backups**: paid Postgres plans include daily
  automatic backups with point-in-time recovery, managed entirely by
  Render - see the `oap-postgres` database's **Backups** tab. This is the
  primary backup mechanism for this deployment and needs no extra setup
  beyond picking a plan that includes it.
- **Off-Render copies** (recommended in addition, not instead of, the
  above - so a copy exists outside Render's own infrastructure too): from
  your own machine, with the `psql`/`pg_dump` client installed:
  ```bash
  pg_dump "$(render_external_database_url)" --format=custom > office_automation_$(date -u +%Y%m%dT%H%M%SZ).dump
  ```
  using the **External Database URL** shown on the `oap-postgres`
  dashboard page (distinct from the internal DSN the app uses - the
  external one is reachable from outside Render for exactly this
  purpose). Store the resulting `.dump` file in your office's existing
  backup location.
- The persistent disk at `/app/data` (documents, exports, archives) is
  not covered by Render's database backups - copy it out separately, e.g.
  via the Shell tab: `tar -czf - -C /app/data archive export import | ...`
  piped to wherever your office keeps off-Render copies, on whatever
  schedule matches your retention needs.

## 11. Production checklist

- **HTTPS** - Render terminates TLS automatically for every
  `*.onrender.com` URL and for custom domains you attach (Settings ->
  Custom Domains), including automatic certificate renewal. No separate
  reverse proxy is needed on Render, unlike the self-hosted Docker path
  in `docs/DEPLOYMENT.md` §5.
- **Backups** - confirm the `oap-postgres` plan includes Render's
  automatic backups (§10), and schedule an off-Render `pg_dump` copy on
  whatever cadence your office's data retention policy requires.
- **Database persistence** - confirm `oap-postgres` shows as a separate,
  persistent resource (not recreated on every deploy) and that the
  `oap-data` disk on `oap-api` shows the expected used/available size
  after documents have been processed - a disk that resets to empty after
  a deploy indicates it was not actually attached as a persistent disk.
- **Monitoring** - use Render's built-in **Metrics** tab (CPU, memory,
  request rate) and set up a notification (Render's own alerting, or an
  external uptime monitor hitting `GET /health`) for deploy failures and
  service downtime. `data/logs/application.log` on the persistent disk
  and the **Logs** tab (structlog also prints to stdout, which Render
  captures) are the two places to check when something looks wrong.
- **Security verification**:
  - `OAP_ENVIRONMENT=production` is set (confirms
    `assert_secure_for_production()` ran at startup - the service would
    have failed to start otherwise if `OAP_ENCRYPTION_KEY` were missing
    or `OAP_SECRET_KEY` were still the placeholder default).
  - `OAP_CORS_ALLOWED_ORIGINS` matches the real service URL exactly (§5) -
    test that a request from an unexpected `Origin` is rejected by the
    browser's CORS enforcement.
  - Confirm `curl -I https://<your-service>.onrender.com/health` shows
    the security headers from `SecurityHeadersMiddleware`
    (`X-Content-Type-Options`, `X-Frame-Options`,
    `Strict-Transport-Security`, etc.).
  - Confirm the `oap-postgres` database has no public `ipAllowList`
    entries (§2) and is not reachable except from `oap-api`.
  - Create the first admin account (§8) and confirm a wrong password is
    rejected and repeated failures trigger the documented account
    lockout (`docs/SECURITY.md`).
